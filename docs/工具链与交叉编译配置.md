# WHEELTEC STM32 工具链与交叉编译配置

> 本文档对应当前工程。新电脑运行 `setup-toolchain.cmd` 即可配置并编译；日常使用 `wt.cmd`，也会自动补齐本项目的固定版本工具。

## 到陌生电脑后的操作

要求 Windows 10/11 x64、PowerShell 5.1 或更高版本，以及能访问 Arm 和 GitHub 的网络。无需管理员权限，也无需安装 Python、Conda、Visual Studio、CubeMX 或 Keil。

将完整工程复制或克隆到新电脑，打开 PowerShell 并进入工程目录，执行：

```powershell
.\tools\download\setup-toolchain.cmd
# 或沿用原命令：
.\wt
```

脚本自动下载固定版本 ZIP、逐包检查 SHA256、解压、验证可执行文件版本，再配置和编译当前工程。HEX/BIN 缺失或早于 ELF 时，`wt` 会补生成。成功后在 `build/` 得到 `WHEELTEC.elf`、`WHEELTEC.hex`、`WHEELTEC.bin` 和 `WHEELTEC.map`。默认 Debug，可加 `-Mode Release`。

| 工具 | 固定版本 | 用途 |
|---|---|---|
| CMake | 3.31.10 Windows x64 | 配置并驱动构建 |
| Arm GNU Toolchain | 12.2.Rel1，GCC/G++ 12.2.1 | Cortex-M3 的 C/C++ 编译，附带 ar、objcopy、size 等 |
| xPack Windows Build Tools | 4.4.1-3，GNU Make 4.4.1 | 本机构建程序，提供 `mingw32-make.exe` 兼容入口 |

GCC 和 G++ 是同一套 Arm 交叉工具链中的两个驱动；MinGW/GNU Make 是 Windows 上组织构建的程序。本工程无需完整 MinGW 主机 GCC 套件。xPack 的原始 `make.exe` 被复制为 `mingw32-make.exe`，保留整个原发行包及许可证。

安装地址和操作：

- 默认 `%LOCALAPPDATA%\WheeltecTool`；用户名路径含非 ASCII 字符时回退到 `%PUBLIC%\WheeltecTool`。
- 可运行 `.\tools\download\setup-toolchain.cmd -ToolsDir D:\WheeltecTool` 指定有写权限的 ASCII 路径，选择记录在本工程的 `.wt-toolchain.json`，该文件不入库。
- 工具仅加入当前构建进程 PATH，不修改用户或系统 PATH，也不依赖原电脑 E 盘或 Conda 环境。
- `.\tools\download\setup-toolchain.cmd -InstallOnly` 只配置，不编译。重复运行会检查并复用已有工具。
- ZIP 缓存在工具目录的 `downloads/` 中。网络中断时重新运行，curl 会续传 `.part`；完整且通过校验的 `.part` 直接复用；服务器不支持续传时保留旧片段并自动从头下载。校验失败的包被隔离，不会解压运行。
- 首次约下载 360 MB，解压需要额外磁盘空间。下载链接、SHA256 和工具目录名固定在 `tools/download/toolchains.psd1`。
- 官方来源：[CMake 3.31.10](https://github.com/Kitware/CMake/releases/tag/v3.31.10)、[Arm 12.2.Rel1 官方 ZIP](https://developer.arm.com/-/media/Files/downloads/gnu/12.2.rel1/binrel/arm-gnu-toolchain-12.2.rel1-mingw-w64-i686-arm-none-eabi.zip)、[xPack Windows Build Tools 4.4.1-3](https://github.com/xpack-dev-tools/windows-build-tools-xpack/releases/tag/v4.4.1-3)。校验值取自对应发行包官方 SHA256 清单。
- 下载失败时检查公司代理或 GitHub/Arm 网络访问；curl 优先遵循 `HTTPS_PROXY` / `ALL_PROXY` 等环境变量，未指定时读取 Windows 系统代理（包括按 URL 判断的 PAC 规则）。也可以在联网电脑配置后，将整个 `WheeltecTool` 目录复制到新电脑，再通过 `-ToolsDir` 指向它；只携带 `downloads/` 中的三个已校验 ZIP 也可离线解压配置。

工程路径含中文时，`wt.ps1` 自动选择 ASCII 目录联接；父目录含中文时优先使用已验证可写的工具目录下的 `source-links/`，避免中文用户名下需要向盘符根写入。旧 `build/` 中的源码路径变化、工具路径失效、工具文件不同或构建模式变化时，会重建缓存。等价的 Windows 8.3 短路径和 MSIX 物理路径不会造成重复配置。脚本支持普通源码目录下的 `build/`；出于清理安全，拒绝自动删除符号链接形式的 `build/`。

## 工程结构与代码分层

```
App/
  main.cpp                         外设初始化与主循环
  Control/
    Control.cpp / Control.hpp      顶层调度：采样、控制、输出
    ControlState.hpp               运行数据和模式
    Config.hpp                     控制参数、阈值与时序
  PendulumController/
    PendulumController.cpp / .hpp  平衡、自动起摆、角速度估计
    Pid.hpp                        PD / PI 调节器
  ButtonHandler/
    ButtonHandler.cpp / .hpp       启动消抖与软件急停
  Hardware/
    BoardHardware.hpp              板级硬件汇总
    Adc.hpp / Motor.hpp / Led.hpp   ADC、电机和 LED 封装

Platform/                   与业务无关的 CubeMX 生成代码
  gpio / adc / tim / dma / usart  外设初始化
  stm32f1xx_it.c            中断向量与 HAL 分发
  stm32f1xx_hal_msp.c       外设底层引脚/时钟
  system_stm32f1xx.c        系统时钟默认值
  syscalls.c / sysmem.c     newlib 桩与堆栈
  startup_stm32f103c8tx.s   启动文件
  main.h / *_hal_conf.h     统一头文件与 HAL 配置

Drivers/                    STM32 HAL + CMSIS
docs/                       工具链说明、历史交接记录
tools/flymcu/FlyMcu.exe       串口烧录程序
```

**调度模型**：TIM1 每 20 ms 只置一个 `tickPending` 标志，`main()` 的超级循环反复调用 `Control::controlLoop()`，后者看到标志才执行一个控制周期。TIM1 提供控制节拍，USART1 和 DMA1 Channel4 中断处理日志发送，SysTick 负责 HAL 毫秒计时；启动键 PA5 每 20 ms 消抖扫描；软件急停 PA2 每轮主循环在节拍判断前检查，优先于启动，松开后不自动重启。菜单、PID 加减、单双击和长按已删除，两键均不使用 EXTI 中断，中断里也不做业务、不调 `HAL_Delay`。

**关于 C++ 的编译方式**：原电脑曾在启用 CXX 语言时在编译器探测阶段崩溃（`0xC0000409`），所以 `.cpp` 是交给 C 编译器并附加 `-x c++ -std=gnu++17 -fno-exceptions -fno-rtti -fno-threadsafe-statics` 编译的，链接仍用 `arm-none-eabi-gcc`。代码里不使用 STL、异常、RTTI 和虚函数，因此不引入 libstdc++；全局对象全部常量初始化（无 `.init_array` 项）。
## 命令行工具 `wt`

工程根目录下两个入口，功能相同：

```text
wt.cmd            给 cmd / 双击用的入口（内部优先调用 pwsh，回退到 powershell）
tools/build/wt.ps1  PowerShell 编译实现，参数都在这里
```

常用命令：

```powershell
.\wt.cmd                        # Debug 构建（默认，-Og -g）
.\wt.cmd -Mode Release          # Release 构建（-Ofast）
.\wt.cmd -Clean                 # 清空 build\ 后完整重建
.\wt.cmd -Open                  # 构建完打开 build\ 目录
.\wt.cmd -Flash                 # 构建完启动 FlyMcu，并把 hex 路径放进剪贴板
.\wt.cmd -Jobs 8                # 指定并行任务数
.\wt.cmd -Quiet                 # 只输出结果
```

工具会自动完成：解析工具链 → 必要时建立 ASCII 目录联接 → 配置 CMake（首次、构建类型或工具路径变化时）→ 编译 → 生成 hex/bin → 打印 FLASH/RAM 占用与烧录提示。退出码：0 成功，2 缺工具，3 无法建立联接，4 配置失败，5 编译失败。

## 五个必须遵守的约束（都是实际踩过的坑）

1. **构建路径必须是纯 ASCII。** 工程目录含中文时，`mingw32-make` 可能按 ANSI 代码页读错路径。`wt.ps1` 自动在父目录、用户缓存目录或盘符下选择可写的 ASCII 路径建立目录联接（名字形如 `wt-src-XXXXXXXX`），构建产物仍落在原工程的 `build/`。不要直接对中文路径执行手动 CMake 构建，也不要用 `subst` 映射到盘符根；盘符根的尾反斜杠可能导致自动重配置失败。

2. **不要启用 CMake 的 ASM 语言。** 启用后编译器探测阶段 `cmake` 进程直接崩溃（退出码 `0xC0000409`），CMake 3.31.10 和 CLion 自带 3.29.6 均复现。当前做法是 `project(WHEELTEC C)`，启动文件用 C 语言编译并加 `-x assembler-with-cpp`：
   ```cmake
   set_source_files_properties(
       Platform/startup_stm32f103c8tx.s
       PROPERTIES LANGUAGE C COMPILE_OPTIONS "-x;assembler-with-cpp"
   )
   ```

3. **不要在 CMakeLists 里预设 `CMAKE_AR` / `CMAKE_OBJCOPY` / `CMAKE_OBJDUMP`。** 预设会让 binutils 探测同样以 `0xC0000409` 崩溃。CMake 会自动在编译器同目录找到 `arm-none-eabi-ar` 等工具。

4. **CMake 只启用 C 语言，C++ 源码用 `-x c++` 编译。** 同时启用 C 和 CXX 时，原电脑上第二个语言的 binutils 探测曾崩溃（同上）。所以 `.cpp` 由 C 编译器代劳：
   ```cmake
   set_source_files_properties(${APP_CPP_FILES}
       PROPERTIES LANGUAGE C
       COMPILE_OPTIONS "-x;c++;-std=gnu++17;-fno-exceptions;-fno-rtti;-fno-threadsafe-statics;-fno-use-cxa-atexit")
   ```
   代价是编译时会出现几条 `-std=gnu11 is valid for C but not for C++` 的警告（CMake 按 C 语言传参导致），可以忽略；链接仍用 `arm-none-eabi-gcc`，不依赖 libstdc++。
5. **`--specs=nosys.specs` 只能出现一次。** 它已通过 `CMAKE_C_FLAGS_INIT` 进入编译/链接行，若再写进 `add_link_options` 会报
   `attempt to rename spec 'link_gcc_c_sequence' to already defined spec 'nosys_link_gcc_c_sequence'` 而链接失败。链接行只额外保留 `--specs=nano.specs`。

## MCU 与编译参数

- CPU：`-mcpu=cortex-m3 -mthumb -mthumb-interwork`。
- 宏：`-DDEBUG -DUSE_HAL_DRIVER -DSTM32F103xB`。
- 链接脚本：`STM32F103C8TX_FLASH.ld`。
- Cortex-M3 无硬件 FPU：不要加 `-mfpu=fpv4-sp-d16` 或 `-mfloat-abi=hard`。
- Debug 默认 `-Og -g`，Release `-Ofast`，MinSizeRel `-Os`。
- 应用层全部使用 `.cpp` / `.hpp`；原 UI 的 C 源文件已移出工程。

## 烧录（FlyMcu 串口 ISP）

1. `.\wt.cmd -Flash`（hex 路径会自动进剪贴板），或直接打开 `tools/flymcu/FlyMcu.exe`。
2. 板子设 `BOOT0=1`、`BOOT1=0`，复位进入串口 ISP；FlyMcu 选 COM 口、波特率 115200，粘贴 hex 路径到“程序文件”，勾选“编程后执行”。
3. 烧完把 `BOOT0` 拨回 0，再复位运行。

工程里已不再保留 DAP-Link 相关文件（`openocd.cfg`、`flash-daplink.ps1` 已删除），只用串口烧录。

## CLion 配置（可选）

CLion 只是可选的编辑/调试前端，构建仍走同一套 CMake。

1. 工程路径含中文时，打开 `wt.ps1` 打印的 ASCII 目录联接路径；纯 ASCII 工程路径可直接打开。
2. Profile 选 `MinGW Makefiles`，构建类型 `Debug`。
3. CMake options 留空即可（编译器由 `CMakeLists.txt` 指定）。
4. 不要复用仓库自带的 `cmake-build-debug/`（其源码目录指向原电脑的 D 盘中文路径，已失效）。

## 关于用 CubeMX 重新生成 CMake 工程

**当前不建议。** 原因：

- 工程已能正常构建；CubeMX 生成的是它自己的一套 `CMakeLists.txt` + 工具链文件，会覆盖现有配置，并丢掉上面第 2、3、4、5 条的修正（这些修正正是让这套工程在本机能编过的前提）。
- 重新生成会重写 `Core/Src`、`Core/Inc` 中的生成区。厂家控制算法若不在 `USER CODE BEGIN/END` 保护区（`Core/Src/*.c` 里的改动会被覆盖），有丢失风险。
- `.ioc` 记录的目标工具链是 MDK-ARM V5.32；CubeMX 的 CMake 生成器需要较新版本 CubeMX，生成结果仍需重新核对编译选项、启动文件和链接脚本。

若确实要做，应作为独立迁移任务：先整目录复制一份、逐文件 diff `.ioc` 与源码、确认自定义代码位置，再生成并对比，保留厂家原版。

## 配置证据

- `CMakeLists.txt`：编译器、CPU 参数、宏、链接脚本、C/C++ 源文件列表与输出格式。

## 给 AI 的配置约束

1. 以本文档上一级、包含 `CMakeLists.txt` 的目录为工程根目录，不依赖原电脑绝对路径。
2. 改动配置前先读 `CMakeLists.txt`、`WHEELTEC.ioc`、`STM32F103C8TX_FLASH.ld`。
3. C 交叉编译器 `arm-none-eabi-gcc`，C++ 用 `arm-none-eabi-g++`（默认不启用 CXX 语言）；固件格式由同目录的 `objcopy` 生成。
4. 保留 Cortex-M3/Thumb 参数、`USE_HAL_DRIVER` / `STM32F103xB` 宏和正确链接脚本；不要把 MinGW 主机 GCC 当 MCU 编译器。
5. 不要重新引入 ASM 语言、不要预设 binutils 变量、不要重复 `--specs=nosys.specs`——这三项都会让构建直接失败。
6. 能生成固件不代表已在倒立摆硬件上验证。烧录方式为 FlyMcu 串口 ISP，不要再引入 DAP-Link/OpenOCD 流程。
